# Deviation log

Append-only. Each entry records: date, what changed, why, and whether the
decision was made **before or after** seeing the affected result.

## 2026-07-30 — torch installed from PyPI rather than the PyTorch CPU index

**What changed.** `GETTING-STARTED-claude-code.md` §1 specifies
`uv pip install torch --index-url https://download.pytorch.org/whl/cpu`.
The project venv now installs `torch==2.13.0` from PyPI instead.

**Why.** Installing from the PyTorch index stamps a `+cpu` local version into
the distribution metadata. `uv pip freeze` then emits `torch==2.13.0+cpu`, a pin
that no index can resolve — PyPI does not publish that local version, and the
PyTorch index does not publish the pinned versions of the other 71 packages.
A clean rebuild from `env/requirements.lock` therefore failed outright,
violating G0.1 criterion 4 ("a fresh environment build from the lockfile
succeeds"). Recovering the `+cpu` pin requires passing both
`--extra-index-url` and `--index-strategy unsafe-best-match` on the command
line — neither can be expressed inside a requirements file, so the lockfile
could never be self-contained, which also breaks G4.1 ("environment rebuilt
from `env/requirements.lock`", no manual intervention).

The PyPI wheel is the same CPU build: `torch.version.cuda` is `None` and no
`nvidia-*` dependencies are pulled on either path. The installed package still
reports `__version__ == '2.13.0+cpu'`; only the metadata version differs, and
that version round-trips through `freeze` → `install` cleanly.

**Timing.** Decided **before** seeing any affected result. No analysis has been
run; COG-BCI is not yet downloaded. Pre-P0.

**Residual risk.** ICLabel runs on torch. If G0.4 misses by 1–2 pp after the
seven-step playbook in `references/gates.md` §G0.4 is exhausted, the prime
suspect remains the Python-vs-MATLAB ICLabel difference flagged in
`GETTING-STARTED-claude-code.md` §1; torch build provenance is a secondary
suspect and should be checked against this entry.

## 2026-07-30 — `env/requirements.lock` re-encoded from UTF-16 to UTF-8

**What changed.** The lockfile was generated by a PowerShell `>` redirect and
was written as UTF-16 LE with a BOM. It is now UTF-8 without BOM, LF endings.
Package set and versions unchanged.

**Why.** `uv` tolerates UTF-16, but any UTF-8 reader — including `pip` — fails
with `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0`.
G4.1 requires a rebuild from a clean clone without assuming the rebuilder uses
`uv`.

**Timing.** Decided **before** seeing any affected result. Pre-P0.

**Note for regeneration.** `uv pip freeze > env/requirements.lock` in PowerShell
reintroduces UTF-16. Regenerate with explicit UTF-8 encoding instead.

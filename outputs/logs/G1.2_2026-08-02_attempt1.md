Three F statistics match the published values exactly at four significant
figures. That is far stronger than the ±20% the gate requires and is strong
evidence the RSME extraction, the cell assignment, the condition mapping and
the ANOVA specification are all identical to the published analysis.

Two discrepancies, neither affecting the verdict:

**Degrees of freedom for RSME.** Published F(2,104); observed F(2,52) with
n = 27 after listwise deletion (2 × 26 = 52). An F matching to four significant
figures cannot come from a different sample, so the published denominator df
appears to be misreported — 104 is the *interaction* error df for a 3×3 design
at n = 27 (4 × 26), which is the most likely origin.

**N-Back error rate.** F is 3.7× the published value while remaining hugely
significant, so the criterion ("significant") is met. The definitions differ:
this analysis uses (misses + false alarms) / 144 trials, derived from triggers.
The published definition is not stated in the references. Direction and
significance agree; magnitude does not. Not a blocker here, but the divergence
metric D_beh in G1.3 is built on this measure, so the definition must be fixed
at G-LOCK.

### Why this is not yet the documented fork

`gates.md` §G1.2 says a Part B failure is a fork in the project rather than a
bug. **That does not apply yet, because this run tested the wrong quantity.**

Band power here was computed from the **P0 covariance diagonals**, which come
from the **machine-learning preprocessing variant**: epoch first, clean each
epoch, automatic epoch rejection disabled. The published band-power results —
the anomaly itself — come from the **descriptive variant**: clean the
continuous signal, *then* epoch. `dataset.md` §7.6 and `pitfalls.md` #1 state
the two variants exist and that mixing them is the single most likely cause of
a reproduction failure. The warning is attached to G0.4, but it applies with
equal force here, in the opposite direction: G0.4 needed the ML variant, and
G1.2 Part B needs the descriptive one.

A second mismatch compounds it. `pitfalls.md` #6: the ML pipeline uses alpha
[8–12] while the descriptive analysis uses [8–13]. `config.yaml` correctly
pins 8–12 for the decoding baseline, and that is the band these power values
were filtered in — but the published alpha claim is an 8–13 result. The
strongest disagreements above are precisely in alpha.

So Part B compared descriptive-variant published results against
ML-variant, 8–12 Hz observations. Declaring "the published EEG validation does
not replicate" on that basis would be wrong, and it is the kind of error that
would be very expensive to retract later: it would rewrite the paper's framing
on an artefact of my own pipeline choice.

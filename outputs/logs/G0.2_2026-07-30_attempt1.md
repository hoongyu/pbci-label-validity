## Result: **FAIL** — one blocking item, entirely on the config side

Every data-side criterion is met. `python -m src.io.inventory` nonetheless
exits 1, on a guard I added deliberately:

```
config.yaml eeg.ecg_channel is 'TP9', which appears in no recording. This
release names the ECG channel ['ECG1']. A drop step keyed on 'TP9' would
silently remove nothing.
```

Two things follow, and both need a human decision rather than a code change.

**1. `config.yaml` is pinned to a channel that does not exist here.**
`eeg.ecg_channel: TP9` came from `GETTING-STARTED-claude-code.md` §2. Left as
is, any exclusion step keyed on that name removes nothing and succeeds
silently. In this release the hazard `dataset.md` §7.3 warns about is already
handled by the data — `ECG1` is typed `ecg`, so `picks='eeg'` excludes it — but
relying on that implicitly is exactly the kind of silent dependency that makes
G0.4 fail for unfindable reasons. The guard converts a silent no-op into a loud
failure. It was **not** resolved by editing `config.yaml`, because that file is
the user's specification.

**2. The gate's own TP9 checklist item cannot pass as written.** It asks to
assert that TP9 is identified as ECG rather than EEG. There is no TP9. The
item was satisfied *in intent* — the ECG channel exists, is uniquely
identified, and is never typed as EEG, asserted across all 87 sessions — but
not *as worded*.

Taken together with the extraction size (35.89 GB vs ~50 GB) and the
undocumented archive-nesting inconsistency, `config.yaml`, `gates.md` and
`dataset.md` all appear to describe a **different revision of COG-BCI** than the
one on Zenodo today. Worth confirming with the mentor that this is the intended
version before P0.3 preprocessing begins; it is cheap now and expensive after
G0.4 fails for reasons nobody can locate.
